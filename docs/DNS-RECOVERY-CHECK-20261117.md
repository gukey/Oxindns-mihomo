# 切网后的 DNS 恢复与错误回退检查

日期：2026-11-17，北京时间。接续[配置复核](CONFIG-REVIEW-20261117.md)。用户确认今早从 Wi-Fi 切换到移动数据；本轮只读检查生产状态，在独立回环实例注入故障，没有切换手机网络或修改生产配置。

## 已确认的缺口

当前国内序列的关键步骤为：

```text
国内缓存 → 有回答则结束 → ChinaDNS
→ 收到 SERVFAIL/REFUSED 则清掉回答
→ 有回答则结束 → 主序列继续至 Mihomo
```

**“收到错误 DNS 响应”和“转发器发生传输错误”是两条不同路径。**

- 两路返回 SERVFAIL/REFUSED：转发器正常返回，后面的规则可以执行，因此现有序列能够回退。
- 两路连接中断或超时：并发转发器返回 Rust `Err`，序列传播错误，后面的规则没有执行，Mihomo 不会被调用。
- 已有真实 NXDOMAIN：按原行为保留，不应无差别转去 Mihomo 生成 Fake-IP。

这项缺口由对应版本源码和手机实际二进制的隔离故障注入共同确认。原国内序列在昨晚精简前后未变，因此不能把它认定为删除自动学习造成的新回归。

## 隔离验证

使用手机 OxiDNS 1.7.1 二进制的独立副本，采用独立名称、目录、日志、API 和 DNS 监听。所有测试服务只监听手机回环地址；仅添加测试端口的 ADB forward，没有 reverse、TUN 或防火墙变更。

保留当前国内缓存参数的内存部分和国内/远端序列，关闭测试缓存持久化。主序列只保留国内调用与最终远端回退，以隔离验证该调用链，不冒充全部生产配置回归。两路国内上游与远端均替换为本机 TCP DNS 应答器；名称仅使用 `.invalid`，回答 TTL 为 0，避免缓存掩盖后续故障。

测试候选使用原生 `fallback` 包住国内转发尝试，备用分支为远端序列；国内尝试仍先清除 SERVFAIL/REFUSED。`always_standby=false`，测试 threshold=6000ms，国内测试超时=500ms，使备用分支由已发生的错误/无回答触发，而非健康查询上的提前竞速。候选未写入生产配置。

最终一轮共 **16 次 TCP 客户端查询**，以下每项各测原序列和候选一次：

| 注入条件 | 原序列结果 | 候选结果 |
|---|---|---|
| 正常国内回答 | 国内真实地址 | 国内真实地址 |
| 国内 SERVFAIL | 调用远端，取得测试 Fake-IP | 同左 |
| 国内 REFUSED | 调用远端，取得测试 Fake-IP | 同左 |
| 国内 NXDOMAIN | 保留 NXDOMAIN | 保留 NXDOMAIN |
| 国内连接关闭 | SERVFAIL；没有调用远端 | 调用远端，取得测试 Fake-IP |
| 国内双路超时 | 约 0.52 秒后 SERVFAIL；没有调用远端 | 约 0.59 秒后取得测试 Fake-IP |
| 国内、备用均超时 | 约 0.52 秒后 SERVFAIL | 约 1.02 秒后 SERVFAIL |
| 故障解除后再次正常回答 | 恢复国内真实地址 | 恢复国内真实地址 |

额外核对应答器查询记录：正常回答和 NXDOMAIN 没有触发备用；原序列的连接关闭/超时用例也没有触发备用。所有预期断言通过；预期 SERVFAIL 是故障用例结果，不应汇总成“16 次全部成功解析”。

候选确实修复了该受控场景的回退缺口，但备用也失败时会增加总等待时间。这里没有采用生产的 5 秒/8 秒超时组合，不能把约 0.59 秒当作上线恢复时延。备用生成 Fake-IP 也不等于互联网可用；若移动网络本身未恢复，实际访问仍可能失败。

### 修正记录器字段的解读

此前的 `has_response=false` 表示请求上下文中没有插件生成的回答。**它不能证明客户端完全没有收到 DNS 包。** 本轮隔离 TCP 测试中，转发失败时服务端最终合成并返回 SERVFAIL。因此应表述为“未通过兜底取得有效解析结果”，不能表述为“一律不回包”。今早原请求的线上的最终 UDP/TCP 报文没有抓取，不能将隔离结果冒充历史抓包。

## DoH 连接是否会重建

检查官方 v1.7.1 标签源码：

- 手机配置的两路 DoH 关闭 HTTP/3，使用 H2 路径；没有配置固定出口网卡。
- H2 发送失败、传输接收错误或连接驱动结束时，会将该连接关闭。
- H2 使用 pipeline pool；单次查询超时的策略为 `Retire`，使对应槽位退出可用状态，在在途引用释放后关闭，后续查询可建立其他连接。
- `idle_timeout=30` 是空闲连接维护参数，不能解释成“切网后必须等 30 秒才允许重连”。

因此，不能说当前实现完全没有连接失效/重建机制。本轮只在 TCP fixture 上验证了错误处理和故障解除后的恢复，**没有对真实 TLS/H2 连接注入切网或黑洞**，也没有修改证书校验设置。

读取到的过滤后系统网络日志没有可用于今早窗口的事件行，未取得精确的接口切换、网络验证成功时点及 H2 连接轨迹。用户确认的切网背景与失败时间相符，但仍不能分辨是移动网络暂未就绪、旧连接/连接池恢复问题，还是其他共同路径故障，更不能证明整个约 19 分钟都由同一个原因造成。

## 后续修复边界

可采用原生 fallback 处理该错误路径，无需改核心或重启整个服务。但正式候选还需按生产语义验证国内 AAAA、NCSI、手动直连、负缓存、Lazy 刷新及客户端等待预算；本轮未将简化夹具配置作为可直接覆盖的生产配置交付。不得为测试恢复而清空 Fake-IP 映射，或用全量重启掩盖连接恢复问题。

真实切网因果验证需在专门观察窗口同步记录网络事件、DoH 连接、查询结果和恢复时间；本轮未主动切换正在使用的手机网络。当前检查确认了一个可修的回退缺口，尚未完成今早 DoH 长时间超时的根因证明。
