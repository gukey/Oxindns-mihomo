# 第三路 UDP 上游隔离测试

日期：2026-11-17。按用户要求测试参考配置中的 `udp://180.184.1.1:53`，对照当前双 DoH。测试期间未修改生产 OxiDNS/Mihomo 配置、节点、缓存文件或防火墙，没有切换手机网络。

## 结论

**当前手机不能直接把这条 UDP 53 配置当作独立第三上游。** 本机 OUTPUT 链会把发往任意目标 UDP/TCP 53 的请求重定向到 OxiDNS 5335。名义上查询远端，实际回到本机 DNS，因此表面提速不能用于证明远端 UDP 更快或能独立救援。

本轮已完成协议与回退的受控测试，并确认实网测试受重定向影响。现网仍保留此前部署的双 DoH + Mihomo 错误兜底，没有加入 UDP 上游。

## 测试方案

使用手机实际 OxiDNS 1.7.1 二进制的独立副本、回环监听、独立缓存和 API，对比三个国内解析分支模型：

| 方案 | 国内解析方式 | 国内全部失败后 |
|---|---|---|
| base | 当前两路 DoH，balanced | Mihomo 兜底 |
| race | 两路 DoH + 第三路 UDP，三路并发，仍为 balanced | Mihomo 兜底 |
| standby | 两路 DoH 失败/无回答后才调用 UDP；阈值 6000ms | UDP 也失败才进入 Mihomo |

三路并发主测试保留现有 balanced 和 H2 设置，避免同时改变选择策略、协议、缓存和节点，混淆第三上游的影响。**作者当前配置实际使用 prefer_positive，并启用一条 DoH 的 HTTP/3；因此本轮不是其整份配置的性能复刻。** 后续单独补测了 prefer_positive 的负响应冲突行为。

范围是国内解析分支，不冒充 APP、全部手动规则、热点或 IPv6 出站的端到端验收。所有测试实例均不启用 TUN，不使用生产缓存数据库。受控应答器仅运行于回环地址，真实第三路使用 UDP，未拿 TCP 模拟 UDP。

## 受控故障结果

临时平台 Java 应答器同时提供 TCP 上游夹具和原生 UDP socket，不安装 APP、不新增常驻服务。最终基础用例为 8 个场景 × 3 个方案，共 24 次查询，国内/UDP 故障预算先缩短为 500ms：

| 注入场景 | base | race / balanced | standby |
|---|---|---|---|
| 正常国内回答 | 国内回答 | 任一路正常回答 | 国内回答，不调用 UDP |
| 双 DoH 超时 | Mihomo 测试 Fake-IP | UDP 测试真实地址 | 等 DoH 失败后取得 UDP 地址 |
| UDP 不可用 | 国内回答 | 国内回答 | 国内回答 |
| 国内与 UDP 全部超时 | Mihomo 测试 Fake-IP | Mihomo 测试 Fake-IP | 等两层失败后进入 Mihomo，等待更长 |
| DoH 稍慢但有正回答，UDP 先返回 NXDOMAIN | 正回答 | 采用 NXDOMAIN | 正回答 |
| 双 DoH 返回 NXDOMAIN，UDP 返回正回答 | NXDOMAIN | 正回答 | 保留 NXDOMAIN |
| 双 DoH SERVFAIL | Mihomo 测试 Fake-IP | UDP 回答 | UDP 回答 |
| 故障解除 | 正常国内回答 | 正常回答 | 正常国内回答 |

以上应答为 `.invalid` 名称的合成测试数据，不是实际业务状态。负响应冲突说明引入新解析器可能改变选择结果，**不是证明该远端解析器真的返回错误答案**。

另使用国内 5 秒、UDP 3 秒预算补测双 DoH 超时：

| 方案 | 取得答案时间 | 答案来源 |
|---|---|---|
| base | 约 5.04 秒 | Mihomo 夹具 |
| race | 约 0.01 秒 | UDP 夹具 |
| standby | 约 5.07 秒 | UDP 夹具 |

这是故障注入条件下的协议行为，不是外网延迟结论。UDP 也失败时，按需备用会延长最坏等待预算；它不能保证网络整体中断时仍能成功。

### 补测作者的 prefer_positive

三路并发切换为作者使用的 prefer_positive 后，独立补测两项冲突：

- UDP 先给 NXDOMAIN，DoH 约 250ms 后给正回答：最终取得正回答，没有复现 balanced 的负响应先行结果。
- DoH 给 NXDOMAIN、UDP 给正回答：最终仍采用正回答。

因此不能把 balanced 下的风险直接写成作者方案必然存在同样问题；选择策略确实有影响。但 prefer_positive 不解决下面的本机重定向问题。

## 实网检查发现：UDP 请求被本机接管

只读检查现网规则，存在：

```text
OUTPUT → OXIDNS_OUT
OXIDNS_OUT: UDP dport 53 → REDIRECT to 5335
OXIDNS_OUT: TCP dport 53 → REDIRECT to 5335
```

这些规则没有给本次隔离解析器设置例外。原两路 DoH 使用 HTTPS，不会因目的端口 53 命中这条规则。

证据互相吻合：

1. 在隔离 OxiDNS 中只配置 `udp://180.184.1.1:53`，向它查询 `www.google.com`，取得 `198.18.x.x` Fake-IP。
2. 对该目标 UDP 53 的定向抓包，应答出现在 **lo 回环接口**；没有观察到该目标的物理出口查询包。
3. 现网目的端口 53 的 REDIRECT 规则解释了为什么应用仍认为应答来自原目的地址：源地址外观不能单独证明数据来自远端。

因此，第三路看似工作，其实复用了当前本机分流和缓存。若直接把同样的 UDP 53 上游加入生产 OxiDNS，可能把查询再送回自身；是否持续递归取决于命中缓存、响应先后及限流，不能将它当作可靠的异协议备用。本轮没有在生产制造这种递归。

## 如何处理已经跑出的延迟数据

发现接管前，完成了两个阶段的随机顺序对照：保留独立本地缓存、绕过测试实例本地缓存。各阶段 12 个计入轮次、10 个公开问题、3 个方案，**各 360 次、合计 720 次计入查询**；每阶段另有 30 次预热，均未计入延迟汇总。720 次查询没有传输错误或非零 RCODE。

但三路并发访问的是生产本机 DNS，而不是已证实的远端第三解析器。绕过测试实例缓存时仍会命中生产 DNS 的缓存；它与直接访问 DoH 的对照条件不等价。**这两阶段数据标记为“不适用于外部上游比较”，不据此宣传提速，也不计算上线收益。**

逻辑请求计数仍可说明测试拓扑：绕过测试实例缓存阶段，含预热每方案 130 次解析，base 发起 260 次 DoH 尝试，race 发起 260 次 DoH + 130 次 UDP 尝试，standby 发起 260 次 DoH、未启动 UDP 备用。这里是转发器的尝试计数，不是实际外网包数或耗电量；race 的 UDP 尝试被本机接管。

[脱敏验证汇总](validation/third-upstream-20261117.json)明确保存有效性标记；完整配置、原始抓包、系统规则和诊断日志留在 Git 忽略目录，不上传。
