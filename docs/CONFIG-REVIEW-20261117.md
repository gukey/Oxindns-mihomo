## 今天的独立真机检查

### DNS 协议与分流

向手机实际 OxiDNS 5335 端口发送 **14 项 UDP + 14 项 TCP，共 28 项查询**，全部收到 NOERROR，无传输错误。范围包括：

- 国内常见服务及 CNAME 链、Google、GitHub、Telegram、Google 服务与下载重定向域名。
- A、AAAA、HTTPS/65、SVCB/64。
- 国内 A 返回真实地址；代表性国外 A 返回 Fake-IP，TTL 为 1。
- 国外 AAAA 返回空成功；国内 AAAA 仍可返回真实 IPv6。

这些测试确认当前路径与既有设计一致，不代表全部域名、所有负响应或 IPv6 端到端均已验收。64/65 仍存在既有路径差异，本轮未改变。

### 下载 CDN

通过手机 HTTP 代理创建真实 CONNECT/TLS 连接，并在连接存活时查询控制器：

| 公开测试目标 | 当前目的地址类别 | 实际命中 | TLS |
|---|---|---|---|
| xn--ngstr-lra8j.com 境内下载主机 | 境内 | AND 条件规则，DIRECT | 证书校验通过 |
| gvt1-cn.com 境内下载主机 | 境内 | AND 条件规则，DIRECT | 证书校验通过 |
| gvt1.com 境外下载主机 | 境外 | 既有 RuleSet，非 DIRECT | 证书校验通过 |

三个主机根路径返回 404；这只证明建立连接并收到 HTTP 响应，不算下载成功。另行请求公开 Android SDK 元数据文件 `repository2-1.xml`：

| 手机访问方式 | HTTP | 完整下载字节数 | 本次耗时 |
|---|---|---|---|
| 不使用显式 HTTP 代理 | 200 | 384,394 | 1.962 秒 |
| 使用本机 Mihomo HTTP 代理 | 200 | 384,394 | 1.874 秒 |

这里的“不使用显式 HTTP 代理”不等于抓包证明绕过所有透明接管。两次耗时不是性能对照，不能据此宣传代理更快。测试未调用账号认证接口，也不替代 Play 商店实际更新验收；此前用户已确认精细规则下可以更新，本轮没有重复该交互。

### 发现的实际异常

当前指标快照显示 `query_total=3847`、`query_error_total=192`；ChinaDNS 的 1993 次调用中记录 195 次超时。两类计数覆盖范围不同：后台刷新也可调用转发器，不能把它们当作同一个错误率。

读取真实查询记录并按昨晚手机部署时间筛选后，得到 **192 条失败，全部发生在今早 08:25～08:44，全部指向 ChinaDNS 双路并发失败，且 has_response=false**。超时错误文本为两路上游均失败、DNS query timeout after 5s。

历史记录还包含第一阶段部署前的 236 条同类失败，说明此类问题并非首次出现在昨晚优化之后；但这不足以确定今早故障的具体原因。不能仅凭两个上游同时失败就断言是手机切网，也不能据此认定内核缺陷。

用户随后确认：该时段离家上班，手机从 Wi-Fi 切换到移动数据。切网背景已得到用户确认，与失败窗口相符；但尚无精确切网时间、接口事件和连接重建轨迹，不能认定整个失败窗口都由切网造成。后续优先检查移动网络可用时点、既有 DoH 连接的失效与重建、重试及超时回退；这些具体机制仍待验证，不能将“旧连接未重建”写成已证实根因。

09:19:05～09:21:11 的指标观察中：

- 总查询增加 153，查询错误仍为 192，未新增。
- ChinaDNS 调用增加 5，错误和超时均未增加。
- Mihomo DNS 调用增加 32，错误和超时均为 0。
- 分别固定到当前配置中的腾讯、阿里 DoH 地址，每路补做 3 次实际 DNS wire 请求，6 次均成功且 NOERROR。

这说明本轮检查时两路国内上游已恢复，不代表今早失败不存在。**现有 SERVFAIL/REFUSED 的 drop_resp 只处理已获得的 DNS 响应；实际记录证明双路传输超时仍可能直接结束请求而没有最终回答，不能宣称所有国内失败都能回退到 Mihomo。** 该转发及序列配置在本次精简中没有变化，应单独验证断链、连接恢复及错误回退，不宜与缓存 TTL 调整捆绑上线。

## 对服务器部分的判断边界

本轮没有连接服务器或验证其当前在线状态，只审阅该提交中的候选生成器、审批材料、验证汇总和部署记录。

记录中的服务器学习退出存在已披露的路径变化：一个原历史学习域名及其子域回归国内静态分类，包含 AAAA 路径变化。手机原先已停用学习，提交中的手机受控回放未发现路径变化。不能将两台设备的影响混为一谈。

服务器部署记录还披露了观察期 79 次 DNS 失败和两次 Mihomo systemd 停止/启动，重启发起方未确认；随后有超过 10 分钟的无新增错误观察窗口。这是合理披露，不应将整轮描述为“零错误部署”，也不能把上游重启归因于本次手机配置精简。

## 前一轮缓存候选的接续结果

11 月 16 日下午的本地隔离测试已完成，但当时尚未提交这部分结果；现在补齐记录。候选仅在已经进入国内解析的敏感 CDN 后缀上使用独立缓存：容量 1024、本地正缓存上限 300 秒、min_positive_ttl=10、ECS 入键、不设 Lazy、不做持久化、不缓存负响应。普通国内缓存保持原样，未接入自动路由学习。

受控 TTL=10 秒实验中，上游地址发生变化后：原缓存过期首查返回旧地址并后台刷新，候选首查取得新地址；原缓存约 0.3 秒后的复查也已更新。**不能把一次 stale hit 描述为健康上游下仍持续错误一小时。**

随机配对实测共 480 次计入查询，排除预热，各组每套配置 60 次，无传输错误或非零 RCODE：

| 查询组 | 原配置 P50 / P95，ms | 候选 P50 / P95，ms | 配对中位差 95% bootstrap 区间，ms |
|---|---|---|---|
| 国内 A | 18.041 / 78.641 | 17.856 / 59.871 | -3.000 ～ 2.402 |
| 国外 A | 17.907 / 33.068 | 18.586 / 47.948 | -1.812 ～ 2.372 |
| Apple HTTPS | 22.938 / 147.774 | 28.644 / 148.676 | -2.473 ～ 4.753 |
| 敏感域名 A | 15.653 / 30.752 | 17.081 / 44.178 | -0.338 ～ 4.567 |

差值方向为候选减原配置，四组区间均跨 0；此样本没有支持整体提速的稳定证据，部分候选点估计更慢。它验证了新鲜度策略差异，未证明收益大于额外上游请求和故障时可用性代价。候选仍未部署，未来若推进，还须覆盖分支跳转后的错误回退、重启和真实下载业务。

今天普通缓存仅约 200 项，容量 4096。当前没有扩容到 8192 的依据。原 Lazy、ECS 不入键和缓存持久化策略未改，第一阶段也就没有解决这些策略的所有 CDN 新鲜度边界。

## 建议保留与后续顺序

1. 保留昨晚的学习退出和重复序列合并；保留已验证的 CDN 条件直连规则。
2. 根据已确认的 Wi-Fi → 移动数据切换背景，核对接口事件并复现 DoH 连接失效、重建与请求恢复；设计错误回退时区分上游故障和明确的 NXDOMAIN，避免无差别改路由。
3. 暂不扩缓存、不恢复持久学习、不用未经证明的参数叠加宣称提速。
4. 守护轮询精简值得作为独立下一阶段，但仓库记录目前只有基线与设计，尚未实施。须先验证进程退出、热点重建及漏事件恢复，再替换轮询。
5. 需要 CDN 新鲜度优化时再单独对照分层缓存，不能直接整份覆盖当前设备配置。

本轮仅新增文档，未修改 Android 源码或构建输入，因此没有重跑 APK 构建。相关验证为真机原生 check、运行哈希核对、协议/下载测试及文档差异和隐私检查。
